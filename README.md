# База конструкций наружной рекламы — Алматы

Внутренний портал отдела: единая база конструкций РТС, НРР и Success Market с картой,
фильтрами и выгрузкой. Работает без сервера, без установки чего-либо и без прав
администратора — это обычные файлы, которые открываются в браузере.

---

## Первый запуск, три шага

### 1. Скачать библиотеки и геоданные (один раз, нужен интернет)

```bash
powershell -ExecutionPolicy Bypass -File fetch-geo.ps1
```

Тянет Leaflet и остальные библиотеки в `vendor\`, линии 10 главных магистралей и полигоны
8 районов Алматы из OpenStreetMap в `geo\`. Занимает около минуты.

Если Overpass или Nominatim не ответили — повторите только геоданные:
`.\fetch-geo.ps1 -SkipLibs`. Портал работает и без них: слой магистралей будет выключен,
фильтр по району пустым, всё остальное — как обычно.

### 2. Собрать базу из исходников

```bash
powershell -ExecutionPolicy Bypass -File build.ps1
```

Читает `input\*.kmz` и `input\*.pptx|pptm`, извлекает фотографии, разбирает адреса,
считает районы и локации, пишет `data\data.js` и `photos\`. Занимает 3–5 минут.

### 3. Открыть

Двойной клик по **`Портал.cmd`**. Админка — `Портал.cmd admin`.

> **Почему через `.cmd`, а не прямо по `index.html`.** Браузер, открытый с диска, не даёт
> странице читать пиксели локальных картинок, и фотографии не попадают в выгрузку PPTX.
> Launcher снимает это ограничение флагом `--allow-file-access-from-files` и отдельным
> профилем браузера. Прав администратора не требует, ваши закладки и пароли не трогает.
> По двойному клику на `index.html` портал тоже откроется — просто PPTX выйдет без фото.

## Что где лежит

| Путь | Что это |
|---|---|
| `index.html` | Публичная часть. **Её и кладите в общую папку отдела.** |
| `admin.html` | Админка. **В общую папку не кладите** — это и есть вся защита доступа. |
| `Портал.cmd` | Запуск в браузере с нужным флагом |
| `data\data.js` | Вся база. Единственный файл, который меняется при правках |
| `photos\full\`, `photos\thumb\` | Фотографии: 1600px для карточки, 400px для списка |
| `vendor\` | Библиотеки (после `fetch-geo.ps1`) |
| `geo\magistrals.js`, `geo\districts.js` | Геоданные из OSM |
| `input\` | Исходные KMZ и презентации подрядчиков |
| `logs\` | Отчёты сборки |

Отделу нужны: `index.html`, `data\`, `photos\`, `vendor\`, `geo\`, `Портал.cmd`.
Папки `input\` и `logs\` и файл `admin.html` в общую папку не идут.

## Как ведётся база

Правки делаются в `admin.html` и сразу пишутся в память браузера, поэтому закрытая вкладка
их не теряет. Но **отдел увидит их только после «Сохранить базу»**: кнопка отдаёт новый
`data.js`, который надо положить в папку `data\` в общей папке.

Есть кнопка «Записать прямо в папку» — она просит один раз указать папку портала и дальше
пишет `data.js` без диалога загрузки. Работает не во всех браузерах; если откажет,
остаётся обычное сохранение.

Кнопка «Отбросить черновик» возвращает к тому `data.js`, который лежит на диске.

## Годовое обновление, когда придёт программа 2027

1. Положите новые KMZ и презентации в `input\` (старые замените).
2. Запустите `build.ps1` ещё раз.

Скрипт сливается со старой базой **по паре подрядчик + код**:

- адреса, координаты и фотографии перечитываются из источников;
- ваши поля — зона, статус, цена, размер, подсветка, разрешение, примечание, скрытие,
  загруженные вручную фото, переопределённый район — **сохраняются**;
- конструкции, исчезнувшие из новой программы, **не удаляются**: получают
  `inProgram = false`, скрываются из публичной части и остаются в базе с историей;
- в конце печатается отчёт: сколько добавлено, сколько сохранено, сколько снято.

Тяжёлое обновление из презентаций делает именно скрипт. Браузерный импорт в админке —
для лёгких файлов: Excel, CSV, KML. Им удобно заливать цены и статусы пачкой.

## Добавление нового подрядчика

Так был подключён Success Market — тот же путь для любого следующего:

1. Положите KMZ (координаты) и, если есть, презентацию с фото в `input\`.
2. В `build.ps1` допишите подрядчика в `$CONTRACTORS` (свой цвет), форматы — в `$FORMATS`
   (свои фигуры маркера), и источник — в `$SOURCES` (какой KMZ каким форматом и презентацией
   считать). Если фото для формата нет — `ppt = $null`, привязка фото просто пропускается.
3. Запустите `build.ps1 -SkipPhotos` и посмотрите отчёт «не опознано как улица» — это чужие
   для словаря названия улиц. Настоящие улицы допишите в `$STREETS`, ориентиры можно
   игнорировать: они всё равно попадают в поле «ориентиры», отчёт только подсказка для
   чистоты словаря.
4. Запустите `build.ps1` уже без `-SkipPhotos` — полная сборка с фотографиями.

Публичная часть и админка ничего не знают о списке подрядчиков и форматов заранее — легенда,
фильтры и иконки строятся из `data.js` на лету. Добавлять подрядчика в `index.html` не нужно.

**Creative City (4-й подрядчик) — отклонение от стандартного пути.** Обычная схема выше
предполагает: один KMZ = один формат = одна презентация с фото, и код (номер) есть у каждой
точки. У Creative City не так:

- `cc-cityboards.kml` — голый `.kml` (не `.kmz`), формат указан на **каждой точке отдельно**
  (ExtendedData `формат(тип места)`), а не на весь файл. `build.ps1` читает голый `.kml`
  напрямую и переопределяет формат по этому полю (LED → `cc_led`, всё остальное,
  включая единичные «билборд»/«скроллер», свёрнуто в `cc_cb`).
- **Кода нет вовсе** ни в KML, ни в PDF с фото (`cc-cityboards.pdf`) — сопоставление фото
  с точками карты сделано **по тексту адреса и порядку**, а не по коду, и часть точек
  осталась без фото или сопоставлена с меньшей уверенностью, чем у остальных подрядчиков.
  Если Creative City когда-нибудь пришлёт версию с кодом на каждую точку — стоит пересобрать
  этот источник заново, точность станет выше.
- Формат «Digital board» (`cc_db`, презентация `cc-digitalboards.pptx`) вообще не имеет
  своего KML — координаты получены один раз вручную: у каждого слайда была короткая ссылка
  на Яндекс.Карты (панораму), она резолвится в lat/lon. Результат лежит в
  `input\cc-digitalboard-coords.csv` (координаты, код, цена, номер слайда) и подключается
  в `build.ps1` как источник без KMZ. Здесь код на каждом слайде есть, поэтому фото
  привязаны **точно, по номеру слайда** (см. `attach-cc-photos.ps1`), а не по тексту.
- Привязка фото для Creative City происходит **не в build.ps1**, а отдельным скриптом
  `attach-cc-photos.ps1` (запускать после `build.ps1`) — она специфична для этого разового
  импорта и не нужна для остальных подрядчиков.

**Ситилайт РТС (новый формат у существующего подрядчика).** `rts-citylight.kml` — голый
`.kml`, 475 точек; названия почти всегда буквально совпадают с заголовками слайдов в
презентациях с фото (`rts-citylight-photos-1.pptx`, `rts-citylight-photos-2.pptx` —
альбом не влез в один файл, `ppt` в `$SOURCES` теперь может быть **массивом** файлов,
не только строкой). Обычное сопоставление по имени слайда покрыло не всё (32 слайда из
107 не совпали дословно — то нет разбивки «№1/№2», то опечатка вроде «Дидж» вместо
«DIGITAL»): добавлен резервный уровень — сопоставление по «голому» адресу (пара улиц без
номера/направления/суффикса), но **только когда он однозначен и на стороне слайда, и на
стороне точки** — если на перекрёстке несколько щитов, угадывать который из них не
подписанный слайд не пытается. Включается точечно через `matchByAddress = $true` у
источника, не для всех остальных. Презентации подписаны «пример пакета» — это не полный
фотокаталог всех 475 точек, а выборка (~180 слайдов, из которых часть — MUPI/LCD-станции
метро, вообще не про этот формат): 79 точек получили фото, остальные — честно без фото,
это не брак сопоставления, а реальный охват источника.

## Города

База готова принять другие города, кроме Алматы. У каждой конструкции есть поле
`city` (`data\data.js` → `cities`: `almaty`, `astana`, `shymkent`, `karaganda` —
последние три заведены заранее, без данных, ради готового фильтра «Город»).
**Город — отдельное измерение от подрядчика**: один город может вмещать разных
подрядчиков (как сейчас Алматы вмещает РТС/НРР/Success Market/Creative City/Citix).

Чтобы добавить данные по новому городу — тот же путь, что и для нового подрядчика
(см. «Добавление нового подрядчика» ниже), плюс у записи в `$SOURCES` в `build.ps1`
дописать `city = 'astana'` (по умолчанию, если не указано, — `'almaty'`). Новый
подрядчик/формат для другого города заводится в `$CONTRACTORS`/`$FORMATS` как обычно.

Список городов сейчас правится только в `build.ps1` (`$CITIES`) — отдельной вкладки
«Города» в админке нет (в отличие от подрядчиков/форматов); в карточке конструкции
и в фильтре списка город показывается и переключается, но добавить новый город
через саму админку нельзя.

**Клик по чипу города переносит карту** к этому городу (координаты — в `$CITIES`
в `build.ps1`) и переключает слой «Главные магистрали» на набор улиц этого города
(`geo\magistrals.js` для Алматы, `geo\magistrals-<город>.js` для остальных —
качаются тем же `fetch-geo.ps1`, теперь по списку городов `$CITY_MAGISTRALS`).
Для города без своего файла магистралей чекбокс просто гаснет (как раньше для
Алматы без `fetch-geo.ps1`).

**Караганда — первый город кроме Алматы с реальными конструкциями** (подрядчик
Mari kz, 107 точек: 98 Билборд + 9 Ситиборд, экспорт Google My Maps). Формат
определялся папкой в исходном файле, а не полем на точке — при подключении
разбит на 2 отдельных `.kml` (по одному файлу на папку/формат), как и у всех
остальных источников. Фото — прямые ссылки в `gx_media_links` (как у Citix),
качаются тем же общим кодом без сопоставления. Свой словарь улиц (Караганда,
не пересекается с Алматы почти совсем) — см. блок `# --- Караганда (Mari kz) ---`
в `$STREETS`. Позже добавлен и Citix в Караганде (14 точек, тот же подрядчик,
что в Алматы, тот же `nameStyle = 'citix'` — просто `city = 'karaganda'` у
источника в `$SOURCES`, ничего специфичного под город писать не пришлось).

**Шымкент — второй город с реальными конструкциями.** Два подрядчика:

- **Citix** (19 точек, формат `citix_smart`/«Smartboard» — свой, отдельный от
  `citix_mb`/«Медиаборд» в Алматы/Караганде). Адрес здесь не в `<name>` (там код
  подрядчика вида `KZ-SHY-TOM-AKR-6`), а в `<description>` вместе с HTML-разметкой —
  добавлена `Extract-CitixShymkentAddress` (снимает теги, декодирует HTML-сущности)
  перед тем, как текст идёт в уже существующий `Normalize-CitixName`.
- **Innoforce** (142 точек, новый, 6-й подрядчик, формат `if_mb`/«Медиаборд» —
  сведён в один чип с Citix/Media Mart) — код (`CIT12.`) и направление
  (`(в.н.)`/`(ю.н.)`/...) зашиты прямо в `<name>`, разбирает новая
  `Normalize-InnoforceName`. Правило «`.` перед словом Остановка → ` - `» намеренно
  сделано узким (не блانкетная замена всех `. `) — часть ориентиров сама содержит
  сокращения с точкой («Б. Момышулы»), и широкая замена ошибочно резала их на две
  улицы.

Оба источника потребовали новых улиц в словаре (Тауке хана, Байдибек би,
Тамерлановское шоссе и другие — блок `# --- Шымкент (Citix/Innoforce) ---`
в `$STREETS`); фото — прямые ссылки в `gx_media_links`, тем же общим кодом,
без сопоставления. Проверка на порчу фото (переиспользование пути между
разными id) — 0 конфликтов; 1 точка Citix осталась без фото (ссылка не
резолвится).

**Астана — третий город.** Citix, экспорт Google My Maps с тремя папками —
при подключении разбит на 3 файла (как Караганда-Mari kz), у каждой свой стиль:

- «TomTom» → формат **Smartboard** (сведён в один чип с Шымкентом — карта сама
  называется «Астана 2025 Smartboards Citix»), 41 точка. Адрес прямо в `<name>`
  («100. Улица - Улица, с.н.») — тот же `nameStyle = 'citix'`, что у Алматы/Караганды,
  без изменений.
- «Cityboards» (8 точек) и «TOM SRG» (1 точка) → код в `<name>`
  (`KZ-AST-CITYBOARD-SRG-N` / `KZ-AST-TOM-SRG-1`), адрес — в `<description>`, тот же
  приём, что у Шымкента (`nameStyle = 'citix_shymkent'`), просто под именами своих
  собственных форматов **Cityboard** и **Tom Tom** (папки подрядчика так называются).

Попутно вскрылись и исправлены два бага, общих для всего Citix-конвейера (не только
Астаны):

- `Normalize-CitixName` всегда возвращала формат (`citix_mb` по умолчанию, если не
  Jumbo/Арбат/Magic Mupi), и вызывающий код **безусловно** его подставлял — это
  затирало формат источника, если он не `citix_mb` (ровно случай Smartboard: все 41
  точки TomTom-папки полу­чили `citix_mb` вместо своего формата, пока не поправили
  на «переопределять, только если реально нашёлся особый префикс»).
- В Астане (в отличие от Шымкента) перед кодом в `<name>` ещё стоит порядковый номер
  экспорта («3. KZ-AST-CITYBOARD-SRG-3») — раньше он утекал прямо в код и в id
  конструкции; теперь срезается тем же приёмом, что и в `Normalize-CitixName`.

Улицы Астаны — новый блок `# --- Астана (Citix) ---` в `$STREETS` (Мангилик Ел,
Туран, Тәуелсіздік и другие; часть уже совпадает с восемью проспектами, которые
`fetch-geo.ps1` качает для слоя магистралей этого города). Заодно исправлены две
мелкие, но общие для всех источников проблемы в `Parse-Address`: двойной префикс
(«ул. Проспект Республики» снимался только один раз, оставляя «Проспект» перед
именем улицы — теперь снимается в цикле) и висячий «№» в номере щита без бара
(«Абылай хан №25» откусывало только «25», оставляя мусор «№» в ориентире — типовая
проблема с любым «слово + номер после №» без разделителя).

Фото — как у Шымкента, прямые ссылки в `gx_media_links`. После общего повторного
прогона докачки (см. «Что осталось сделать руками») без фото остались 3 точки
Smartboard из 41 — ссылки не резолвились ни с первой, ни со второй попытки.

Для Астаны найдены все 8 запрошенных проспектов/улиц. Три из них не находились
по `name:ru`, угаданному по написанию, пока не сверили точные значения тегов
через Nominatim/Overpass: «Мәңгілік Ел» записан в OSM как
`проспект Мангилик Ел` (русская транслитерация, без казахских букв), «Кабанбай
батыра» — как `проспект Кабанбай Батыра` (с заглавной «Б»), «Сарайшық» — как
`улица Сарайшык` (без казахской «қ»). Если для нового города улица не находится
с первой попытки — стоит так же свериться с реальными тегами на openstreetmap.org
(или через Nominatim), а не только менять написание на слух, и поправить
`$CITY_MAGISTRALS.<город>.streets` в `fetch-geo.ps1`.

Overpass периодически недоступен (перегружен) на несколько минут — если
`fetch-geo.ps1` не находит улицу, которая находилась раньше, это может быть
временный сбой сервиса, а не пропавший тег: стоит повторить позже
(`powershell -ExecutionPolicy Bypass -File fetch-geo.ps1 -SkipLibs`), а не сразу
переписывать словарь улиц.

## Решения, заложенные в устройство базы

**Дубли между подрядчиками не склеиваются.** Один физический щит не принадлежит двум
подрядчикам одновременно — близкие точки означают, что на перекрёстке стоят *разные*
конструкции разных владельцев. Поэтому вместо склейки есть **локации**: в карточке видно
«на этой же локации ещё столько-то», а в подборке появляется предупреждение о пересечении.
Ни одна запись при этом не теряется.

**Локация — это пара улиц, а не радиус.** Все конструкции на `Абая × Сейфуллина` попадают
в одну локацию независимо от того, 30 между ними метров или 90: это физически один
перекрёсток. Радиус 50 м работает только там, где вторую улицу распознать не удалось
(ориентиры вроде `МЕТРО САЙРАН`, одиночные адреса вроде `АЭРОПОРТ №1`). Чистый радиус
давал цепочки: А ближе 50 м к Б, Б к В — и два разных перекрёстка склеивались в один.

**Конструкция принадлежит обеим улицам перекрёстка.** Щит на `Абая × Сейфуллина` находится
и по фильтру «Абая», и по фильтру «Сейфуллина» — он виден с обеих. Порядок улиц в названии
ничего не значит: у РТС `Богенбай батыра – Абылай хана`, у НРР тот же перекрёсток записан
наоборот.

**Улицы — выверенный справочник, а не разбор строки.** В данных подрядчиков `МОМЫШ УЛЫ`
и `МОМЫШУЛЫ` — одна улица, `НАЗАРБАЕВА` и `Н.НАЗАРБАЕВА` — одна, а `РЫСКУЛОВА`
и `РЫСКУЛБЕКОВА` — **разные**. При этом `СК ДОСТЫК` и `ТРЦ ДОСТЫК ПЛАЗА` — не улица Достык,
а ориентиры. Автоматически это не разделить, поэтому есть словарь с алиасами: правится
на вкладке «Улицы», опечатки подрядчиков в алиасах оставлены намеренно.

**Галочка «главная» = слой магистралей.** Отдельной сущности «магистраль» нет: слой строится
по улицам с галочкой. Добавите новую главную — фильтр заработает сразу, а вот линия на карте
появится только после того, как улицу допишут в список в `fetch-geo.ps1` и скрипт
перезапустят: геометрия берётся из OSM.

**Район и зона считаются по координатам.** Район — из полигонов OSM, зона — из ваших
многоугольников. Передвинули границу зоны в админке — все точки переразметились сами.
Отдельную точку можно переопределить вручную в её карточке.

- **12 точек Citix — без фото** (8 Медиаборд в Алматы, 3 Smartboard в Астане,

  30 сек и 2 попытки на ссылку вместо одной) отыграла обратно 27 из 39 точек,

  не поддались и повторным попыткам. Битые файлы удалены, ссылка на фото у этих
  точек честно пустая — лучше «нет фото», чем наполовину чёрная картинка. Когда
  сеть станет стабильнее, можно запустить `retry-citix-photos.ps1` ещё раз.

  Word испортила ~80% картинок (превратила в мусор высотой 1 px — баг рендеринга на большом
  документе), а точное сопоставление оставшихся живых фото (`input\cc-raw-jpegs\`, 312 шт.,

  Word для рендера страниц, попросить у Creative City версию с кодом на каждую точку, либо

- **10 точек Ситиборда и 1 точка Медиаборда Media Mart — без фото.**

## Если что-то не работает

| Симптом | Причина и что делать |
|---|---|
| «Не загрузилась библиотека Leaflet» | Не запускали `fetch-geo.ps1` |
| «Не найден data/data.js» | Не запускали `build.ps1` |
| Слой магистралей серый, район пустой | Нет `geo\*.js` — `.\fetch-geo.ps1 -SkipLibs` |
| Карта серая, тайлы не грузятся | Нет интернета или IT режет `tile.openstreetmap.org` |
| Спутник не работает, схема работает | IT режет `server.arcgisonline.com` — не критично |
| PPTX выгрузился без фотографий | Открыли не через `Портал.cmd` |
| `build.ps1` ругается на кодировку | Файл должен быть в UTF-8 **с BOM** — PowerShell 5.1 иначе читает кириллицу как ANSI |
